# Описание проекта «Инвестиционный процессор» (Invest AI)

Этот документ объясняет простым языком, **что это за проект, как он устроен, и почему
при разработке приняты именно такие решения**. Он будет полезен новому разработчику,
который только знакомится с кодом, и человеку, который хочет понять идею целиком, не
читая весь исходник.

---

## 1. О чём вообще проект

«Инвестиционный процессор» — это **внутренний веб-сервис компании для управления
инвестиционными заявками**. Представьте крупную компанию, где разные команды постоянно
приходят к финансистам с идеями: «дайте денег на новый продукт», «выделите бюджет на
маркетинг», «вложитесь в этот проект». Раньше всё это считалось в Excel и согласовывалось
в переписке. Этот сервис заменяет такой хаос на единую систему.

Что он умеет:

1. **Создавать заявки на инвестиции** через пошаговый мастер (визард).
2. **Автоматически считать финансовую модель** — NPV, IRR, окупаемость, LTV/CAC и
   десяток других метрик — прямо в браузере, в реальном времени.
3. **Подключать искусственный интеллект**: AI пишет описание проекта, оценивает риски,
   ищет аномалии в цифрах и даёт рекомендации.
4. **Вести жизненный цикл заявки**: черновик → отправлена на согласование → одобрена /
   отклонена.
5. **Разграничивать права** между ролями: заявитель (owner), финансовый директор (CFO),
   менеджер, генеральный директор (CEO).
6. **Сопровождать одобренный проект**: транши (поэтапное финансирование), план/факт
   (сравнение прогноза с реальностью), комментарии, вложения, уведомления.
7. **Выгружать отчёты** в PDF и Excel.

То есть это не просто «калькулятор», а полноценная система документооборота вокруг
инвестиционных решений с финансовым движком и AI внутри.

## 2. Главная идея архитектуры: «два звена и одно API»

Проект построен по простой и проверенной временем схеме — **двухзвенная архитектура**:

```
┌──────────────┐    HTTP/HTTPS    ┌─────────────────┐
│   Браузер    │ ───────────────► │   Nginx :80/443 │
│ (HTML +      │                  │ (reverse proxy  │
│  Alpine.js)  │ ◄─────────────── │  + раздача      │
└──────────────┘                  │  статики)       │
                                  └────────┬────────┘
                                           │
                       ┌───────────────────┴────────────────┐
                       │                                     │
              статика (HTML/JS/CSS)               /api/* → проксирование
                                          ┌────────────────▼──────────┐
                                          │  FastAPI (Uvicorn, 2 worker)│
                                          └──────┬───────────────┬─────┘
                                                 │               │
                                       ┌─────────▼──┐     ┌──────▼─────────┐
                                       │ SQLite /   │     │ AI-провайдеры: │
                                       │ PostgreSQL │     │ OpenAI /       │
                                       └────────────┘     │ Anthropic /    │
                                                          │ RouterAI       │
                                                          └────────────────┘
```

- **Frontend** — это набор обычных HTML-страниц с «оживляющим» их JavaScript-фреймворком
  Alpine.js. Никакой сборки, никакого Webpack/Vite — файлы открываются как есть.
- **Backend** — Python-приложение на FastAPI, которое отдаёт **REST API** по адресам
  `/api/v1/...`.
- **Nginx** стоит спереди: он отдаёт статические файлы фронтенда и проксирует все запросы
  `/api/*` на backend. Заодно занимается HTTPS и сжатием.
- **База данных** — SQLite в разработке, PostgreSQL в продакшене (код это поддерживает без
  изменений).
- **AI** — внешние сервисы (OpenAI, Anthropic, или агрегатор RouterAI), которые
  вызываются по HTTP.

### Почему именно так?

- **Простота превыше моды.** Команда сознательно не стала делать «модный» SPA на React с
  отдельным фронтенд-билдом. Для внутреннего корпоративного инструмента это лишняя
  сложность: нужен Node, сборка, CI для фронта, версионирование бандлов. Здесь же —
  открыл HTML, и он работает. Это резко снижает порог входа и стоимость поддержки.
- **Чёткое разделение.** Фронт ничего не знает о базе, бэк ничего не знает о вёрстке. Они
  общаются только через документированный JSON-API. Можно переписать любую сторону
  независимо.
- **Nginx как единая точка входа** убирает проблему CORS в продакшене (фронт и API на
  одном домене) и даёт бесплатно HTTPS, кэширование, сжатие.

## 3. Backend (Python / FastAPI)

### 3.1. Структура папок

```
backend/app/
├── main.py            # точка входа: создаёт FastAPI, подключает все роуты
├── config.py          # настройки из .env (через pydantic-settings)
├── database.py        # подключение к БД, сессии, инициализация, миграции «на лету»
├── auth.py            # пароли (bcrypt), JWT-токены, проверка ролей
├── settings_store.py  # настройки, которые меняются в рантайме (API-ключи, бюджет)
├── models/            # таблицы БД (SQLAlchemy ORM)
├── schemas/           # описания входных/выходных данных (Pydantic)
├── api/v1/            # эндпоинты, сгруппированные по темам
└── services/          # бизнес-логика: финансы, AI, экспорт, e-mail, уведомления
```

Это классическое для FastAPI разделение на **слои**, и оно выбрано не случайно:

- **models** — «как данные лежат в базе».
- **schemas** — «как данные приходят и уходят по API» (валидация, преобразование).
- **api/v1** — «какие есть URL-адреса и кто имеет к ним доступ» (тонкий слой).
- **services** — «где живёт реальная логика» (расчёты, обращения к AI).

Зачем разделять schemas и models, если они похожи? Потому что **то, что хранится в базе,
и то, что показывается наружу — это разные вещи**. Например, в базе есть
`hashed_password`, но в API он никогда не должен попасть. Pydantic-схемы гарантируют, что
наружу уйдёт только разрешённое.

### 3.2. Почему FastAPI

- **Автоматическая валидация.** Описываешь Pydantic-модель — FastAPI сам проверяет
  входные данные и возвращает понятную ошибку 422, если что-то не так. Не нужно писать
  тонны ручных проверок.
- **Бесплатная документация.** На `/api/docs` сразу есть Swagger UI со всеми эндпоинтами —
  удобно тестировать и показывать.
- **Скорость и современность** — типизация, async-возможности, активное развитие.

Интересная деталь: **роуты написаны синхронно, а не async**. Это осознанный выбор —
работа идёт с синхронным SQLAlchemy, а нагрузка у внутреннего инструмента небольшая.
Смешивать async-роуты с синхронными запросами к БД опаснее (можно заблокировать event
loop), чем просто оставить всё синхронным. FastAPI в этом случае сам выполняет такие
роуты в отдельном пуле потоков.

### 3.3. Хранение данных и «миграции на лету»

В `database.py` есть любопытное решение. При старте приложения (`init_db`) код не только
создаёт недостающие таблицы, но и **пытается добавить новые колонки** в уже существующие
таблицы:

```python
for col_def in [
    "ALTER TABLE projects ADD COLUMN value_score_data JSON",
    "ALTER TABLE projects ADD COLUMN smart_contract_data JSON",
    ...
]:
    try:
        conn.execute(text(col_def))
    except Exception:
        pass  # колонка уже есть — игнорируем
```

**Почему так, а не Alembic (полноценные миграции)?** Alembic в зависимостях есть, но в
ход пошёл упрощённый подход: добавление колонки обёрнуто в `try/except`, и если колонка
уже существует — ошибка просто проглатывается. Это **идемпотентно** (можно запускать
сколько угодно раз) и не требует отдельного шага «накати миграции» при деплое. Для
небольшого проекта с простой эволюцией схемы (в основном добавление JSON-полей) это
прагматично и экономит время. Минус — это не отслеживает удаление/изменение колонок, но
здесь такого почти не бывает.

Ещё одно решение — **гибкое хранение через JSON-колонки**. Вся финансовая модель проекта
лежит в одном поле `financial_model` типа JSON, рассчитанные метрики — в `metrics`, данные
AI-рисков — в `risks_data`, данные смарт-контракта — в `smart_contract_data` и т. д. Это
позволяет менять структуру формы на фронте, **не меняя схему базы каждый раз**. Гибкость
в обмен на строгость — оправданный размен для продукта, который активно меняется.

### 3.4. Сидинг пользователей

При первом запуске, если таблица пользователей пуста, автоматически создаются два
служебных аккаунта — CEO и CFO (логины/пароли берутся из переменных окружения
`SEED_CEO_*`, `SEED_CFO_*`). Это избавляет от ручного создания первого админа: поднял
систему — и сразу можешь зайти.

## 4. Аутентификация и роли — кто что может

### 4.1. Как работает вход

- Пользователь логинится по **email + пароль** (`POST /api/v1/auth/token`).
- Пароли хранятся не в открытом виде, а как **bcrypt-хеши** (библиотека `passlib`).
- В ответ выдаётся **JWT-токен** (подписан алгоритмом HS256, живёт 8 часов). Фронт хранит
  его и прикладывает к каждому запросу в заголовке `Authorization: Bearer ...`.
- В токене зашиты `email`, `role` и `user_id` — этого достаточно, чтобы на каждый запрос
  понимать, кто пришёл и что ему можно.

**Почему JWT, а не серверные сессии?** JWT не требует хранить состояние на сервере — токен
самодостаточен. Это упрощает масштабирование (можно поднять несколько копий backend без
общего хранилища сессий) и хорошо ложится на «фронт = статика + API».

### 4.2. Ролевая модель

Есть четыре роли, и логика прав «зашита» в зависимости FastAPI (`auth.py`):

| Роль | Кто это | Что может |
|------|---------|-----------|
| **owner** | Заявитель | Создаёт и редактирует **свои** заявки, отправляет на согласование. Видит только свои проекты (кроме одобренных — те видны всем). |
| **manager** | Менеджер | Согласовывает/отклоняет заявки, видит все проекты. |
| **cfo** | Фин. директор | Всё, что менеджер, плюс настройки системы, управление пользователями, API-ключами. |
| **ceo** | Гендиректор | Только смотрит. Не создаёт, не редактирует, не удаляет — «режим наблюдателя». |

Права проверяются двумя способами:
- **Через зависимости** вроде `require_cfo`, `require_approver` — для целых эндпоинтов.
- **Внутри обработчика** — для тонких случаев (например, owner может редактировать проект,
  только если это его проект и он в статусе «черновик» или «на согласовании»).

Такой подход — права рядом с кодом, который их использует — делает логику прозрачной:
видно прямо в обработчике, кому и что разрешено.

## 5. Финансовый движок — сердце проекта

Это самая «инженерно интересная» часть. Здесь принято необычное, но обоснованное решение:
**финансовая модель считается в двух местах одновременно — в браузере и на сервере**.

- **`frontend/js/finance.js`** — чистый JavaScript, считает всё в реальном времени.
- **`backend/app/services/finance_service.py`** — тот же расчёт на Python (numpy).

### Зачем дублировать?

- **На фронте** расчёт нужен для **мгновенной обратной связи**. Пользователь меняет цену
  или конверсию — и тут же видит, как поплыли NPV и IRR, без единого обращения к серверу.
  Это делает работу с моделью живой и приятной. Реализовано через `$watch` Alpine.js: при
  любом изменении формы вызывается `Finance.calculate()`.
- **На бэке** тот же расчёт — это **источник истины**. Когда проект сохраняется, сервер
  пересчитывает метрики сам (`_recalc_and_save`) и записывает их в базу. Нельзя доверять
  цифрам, пришедшим с клиента, — их легко подделать или сломать. Поэтому финальные метрики
  всегда считает сервер.

В обоих файлах прямо в комментариях написано: формулы реализуют спецификацию (пункты
1.1.x и 1.2.x) и **должны давать идентичный результат**. Это требование «зеркальности»
держит две реализации в синхроне.

### Что именно считается

Движок строит из вводных данных целые таблицы по годам и кварталам:

1. **Таблицы пользователей**: всего → платящие (через конверсию) → с учётом оттока
   (churn) → новые платящие за период.
2. **Выручка** по одной из трёх моделей:
   - **subscription** — подписка: платящие × цена;
   - **transactional** — транзакции × средний чек;
   - **hybrid** — сумма того и другого.
   Цену можно индексировать по годам (инфляция).
3. **Затраты** — гибко, по строкам, каждая в своём режиме: вручную, % от выручки, % от
   других затрат, или CAC (затраты на привлечение клиента).
4. **Денежные потоки** по годам, ставка дисконтирования = ключевая ставка + премия за
   риск.

И на основе этого — ключевые метрики:

| Метрика | Простыми словами |
|---------|------------------|
| **NPV** | Сколько проект «стоит сегодня» с учётом, что деньги завтра дешевле денег сегодня. Положительный — хорошо. |
| **IRR** | Доходность проекта в процентах годовых (считается методом Ньютона). |
| **DPP** | За сколько лет проект окупится с учётом дисконтирования. |
| **PI** | Сколько отдачи на каждый вложенный рубль. |
| **CAC** | Сколько стоит привлечь одного платящего клиента. |
| **ARPA / ARPU** | Средняя выручка с одного платящего. |
| **LTV** | Сколько денег клиент принесёт за всё время жизни. |
| **LTV/CAC** | Главный показатель здоровья юнит-экономики: зарабатываем мы на клиенте больше, чем тратим на его привлечение, или нет. |

### Поддержка нескольких продуктов и разной детализации

Модель умеет считать **сразу несколько продуктов** (multi-product) — каждый со своими
параметрами, а потом суммирует их таблицы. При этом старый «однопродуктовый» формат тоже
поддерживается ради совместимости со старыми проектами. Также данные можно вводить с
разной детализацией (по кварталам или по месяцам) — `granularity`.

### Защита от «грязных» данных

Форма на фронте часто присылает пустые строки вместо чисел (`nwc: ''`). Чтобы Pydantic не
падал, в схемах `finance.py` есть **санитайзеры** (`_f`, `_f1`, `_f2`,
`model_validator(mode='before')`), которые превращают `None`/`''`/мусор в `0.0` ещё до
валидации. Это типичная «защита на границе»: внешним данным не доверяем, чистим на входе.

## 6. AI-слой — гибкость в выборе провайдера

AI используется для четырёх задач (`services/ai_service.py`):

1. **Генерация описания** проекта по ключевым полям.
2. **Оценка рисков и допущений** на основе финансовых метрик.
3. **AI Risk Score** для операционных заявок (оценка рисков, рекомендация маршрута
   согласования).
4. **Анализ аномалий** и сравнение с портфелем, а также анализ «план vs факт».

Самое интересное решение здесь — **сменный AI-провайдер**. Код умеет работать с тремя:

- **OpenAI** (модели GPT),
- **Anthropic** (Claude),
- **RouterAI** — российский агрегатор-прокси к разным моделям.

Выбор провайдера хранится в настройках (`settings_store.get_ai_provider()`), и функция
`_chat()` просто перенаправляет запрос в нужную реализацию:

```python
def _chat(prompt, max_tokens=700):
    provider = settings_store.get_ai_provider()
    if provider == "anthropic":
        return _chat_anthropic(prompt, max_tokens)
    if provider == "routerai":
        return _chat_routerai(prompt, max_tokens)
    return _chat_openai(prompt, max_tokens)
```

**Почему это важно?** Сервис задумывался для российской компании, а у OpenAI/Anthropic
есть ограничения доступа из РФ. Возможность переключиться на RouterAI (или любой
OpenAI-совместимый шлюз) без переписывания кода — это **страховка от внешних рисков**.
Архитектурно это паттерн «стратегия»: единый интерфейс, несколько взаимозаменяемых
реализаций.

Ещё две практичные детали:
- **Ответы AI просят строго в JSON**, а функция `_strip_fences` снимает обёртку
  ```` ```json ```` , если модель её добавила. Если JSON всё-таки не распарсился — функция
  возвращает «безопасную заглушку», а не падает. То есть **сбой AI не ломает приложение**.
- **Ключи AI вводятся в интерфейсе** (страница настроек, доступная только CFO) и хранятся
  в файле. Но переменные окружения всегда главнее ключей из файла — это позволяет в
  продакшене задать ключ через `.env`, а в простых сценариях — прямо через UI.

## 7. Дополнительные модули вокруг проекта

Помимо ядра (проекты + финансы + AI), есть набор модулей, которые превращают калькулятор в
полноценную рабочую систему:

| Модуль | Файлы | Зачем |
|--------|-------|-------|
| **Транши** | `models/tranche.py`, `api/v1/tranches.py` | Поэтапное финансирование одобренного проекта. У транша есть чек-лист триггеров (условий выдачи) и история изменений. |
| **План/Факт** | `models/fact_entry.py`, `api/v1/fact.py` | Сравнение прогноза с реальными цифрами по месяцам, импорт из файла, прогноз и AI-комментарий по отклонениям. |
| **Комментарии** | `models/comment.py`, `api/v1/comments.py` | Обсуждение проекта внутри карточки. |
| **Вложения** | `models/attachment.py`, `api/v1/attachments.py` | Загрузка файлов к проекту (отдаются через защищённый эндпоинт, не напрямую). |
| **Уведомления** | `models/notification.py`, `api/v1/notifications.py` | Колокольчик в интерфейсе: «вашу заявку одобрили», «новая заявка на согласование». |
| **E-mail** | `services/email_service.py` | Письма при регистрации (с паролем), смене статуса, сбросе пароля (SMTP). |
| **Статистика** | `api/v1/stats.py` | Агрегаты для дашборда: суммарный NPV, средний IRR, число высокорисковых и т. д. |
| **Экспорт** | `services/export_pdf.py` (WeasyPrint), `export_excel.py` (openpyxl) | Выгрузка отчётов в PDF и Excel, опционально с AI-резюме портфеля. |
| **Смарт-контракты** | поле `smart_contract_data`, отдельные страницы | Отдельный тип заявки с майлстоунами, командой, куратором, расчётом вознаграждения через курс NAV. |

Связи между таблицами настроены через SQLAlchemy `relationship` с
`cascade="all, delete-orphan"` — то есть при удалении проекта автоматически удаляются его
комментарии, вложения, транши и факт-записи. Это избавляет от «висячих» строк в базе.

Обратите внимание на деталь в обработчике смены статуса (`projects.py`): уведомления и
письма отправляются в блоках `try/except`, которые **никогда не блокируют ответ**. Логика
здесь: «если письмо не ушло — это не повод заваливать пользователю операцию». Основное
действие (смена статуса) важнее побочного (нотификация).

## 8. Frontend (HTML + Alpine.js)

Фронт — это набор самостоятельных HTML-страниц:

- `login.html`, `register.html`, `reset-password.html` — вход и регистрация;
- `main.html` — дашборд (KPI + последние проекты);
- `new.html` — мастер создания проекта в несколько шагов;
- `project-list.html` — портфель проектов с фильтрами;
- `project.html`, `op-project.html`, `smart-contract.html` — карточки разных типов
  проектов;
- `settings.html`, `users.html`, `profile.html` — администрирование;
- `export.html` — выгрузка отчётов;
- `js/finance.js` — финансовый движок, `js/auth.js` — работа с токеном.

### Почему Alpine.js, а не React/Vue

Alpine.js — это «фреймворк для тех, кому не нужен фреймворк». Он добавляет реактивность
(`x-data`, `x-model`, `$watch`) прямо в HTML-атрибутах, **без сборки и без виртуального
DOM**. Для этого проекта это идеально:

- нет шага сборки → проще деплой и отладка;
- логика страницы видна прямо в разметке;
- порог входа минимальный — любой, кто знает JS, разберётся за час;
- реактивность всё равно есть — поля формы и расчёты обновляются мгновенно.

Минус подхода — при росте сложности страницы становятся большими (например, `new.html` —
это объёмный файл с большой Alpine-моделью). Но для внутреннего инструмента это приемлемый
размен в пользу простоты.

Библиотеки (Alpine.js, Font Awesome) подключаются с **CDN** — снова ради отсутствия
сборки.

## 9. Инфраструктура и деплой

### Docker Compose

Вся система поднимается одной командой `docker compose up -d`. В `docker-compose.yml` два
сервиса:

- **backend** — собирается из `backend/Dockerfile` (Python 3.11 + системные библиотеки для
  WeasyPrint), запускается через Uvicorn в 2 воркера, данные (`/data`) лежат в Docker-томе,
  чтобы переживать перезапуски.
- **nginx** — официальный образ, отдаёт статику и проксирует API.

Интересная деталь: код приложения и фронтенд **примонтированы как volume** прямо в
контейнер (`./backend/app:/app/app`). Это значит, что в разработке можно править код без
пересборки образа — удобно.

### Nginx

`nginx/nginx.conf` решает несколько задач сразу:
- редирект с HTTP на HTTPS, TLS-сертификаты (Let's Encrypt);
- проксирование `/api/` на backend с увеличенными таймаутами (AI-запросы долгие) и лимитом
  загрузки 26 МБ;
- раздача статики с правильным кэшированием — **HTML-файлы намеренно не кэшируются**
  (`no-cache`), чтобы новый деплой сразу был виден пользователям, а вот аватарки можно
  кэшировать на сутки;
- базовые security-заголовки (`X-Frame-Options`, `X-Content-Type-Options`).

### SQLite → PostgreSQL

В разработке используется **SQLite** — файл на диске, ничего не надо устанавливать. В
продакшене достаточно поменять `DATABASE_URL` на PostgreSQL — код в `database.py` сам
определит тип базы (для SQLite добавляется `check_same_thread=False`). Это удобный
«мягкий» путь: начать на простом, вырасти в серьёзное без переписывания.

### Настройки и секреты

- Статичные настройки (URL базы, секрет JWT, CORS) читаются из `.env` через
  `pydantic-settings` (`config.py`).
- Динамические настройки, которые меняются в рантайме через UI (API-ключи AI,
  инвестиционный бюджет, курс NAV, разрешённый домен регистрации), хранятся в отдельном
  JSON-файле (`settings_store.py`) на том же Docker-томе, что и база. Так они переживают
  обновления кода. Переменные окружения при этом всегда имеют приоритет над файлом.

## 10. Сквозные принципы — что объединяет весь код

Если выделить «философию» проекта одной фразой — это **прагматичная простота**. Конкретные
принципы:

1. **Не доверяй данным с клиента.** Финальные финансовые метрики считает сервер; входные
   данные санитизируются; права проверяются на бэке, а не только в интерфейсе.
2. **Сбой во второстепенном не должен ронять главное.** Письма и AI обёрнуты в `try/except`
   с разумными заглушками — основная операция доходит до конца в любом случае.
3. **Гибкость через JSON и сменные провайдеры.** Структура формы и выбор AI могут меняться
   без переписывания базы и логики.
4. **Минимум инфраструктуры.** Нет сборки фронта, нет тяжёлых миграций, нет лишних
   сервисов — всё поднимается одной командой.
5. **Зеркальность фронта и бэка** в финансовых расчётах: быстрый предпросмотр на клиенте +
   достоверный расчёт на сервере.
6. **Всё на русском** — интерфейс, сообщения об ошибках, AI-промпты, потому что это
   инструмент для русскоязычной команды.

## 11. Что стоит улучшить (честно о слабых местах)

Чтобы картина была полной:

- **Нет автотестов** — ни для финансового движка, ни для API. Для системы, считающей
  деньги, это риск; «зеркальность» фронта и бэка проверяется только глазами.
- **Самописные миграции** через `try/except ALTER TABLE` удобны, но не отслеживают сложные
  изменения схемы. При росте проекта стоит перейти на полноценный Alembic (он уже в
  зависимостях).
- **Объёмные HTML-страницы.** `new.html` и подобные файлы большие — это плата за отсутствие
  компонентного фреймворка.
- **AI-ключи в JSON-файле** — практично, но менее безопасно, чем секрет-хранилище; для
  чувствительных сред лучше переменные окружения (что код и позволяет).
- **Документация местами расходится** с кодом (например, упоминания только OpenAI или
  только Claude в разных файлах) — реально поддерживаются три провайдера сразу.

Эти пункты не критичны для внутреннего инструмента на стадии активной разработки, но
полезны как ориентир для развития.
